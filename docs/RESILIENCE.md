# 회복탄력성 설계 (Resilience)

이 프로젝트의 서버는 느리고(응답 5~7초), 간헐적으로 실패하고(429/503), 요청 제한이
있는 외부 AI API를 감싸는 게이트웨이다. 그래서 "얼마나 많이 처리하느냐"가 아니라
"외부가 흔들려도 내 서버가 어떻게 버티느냐"가 핵심 문제다.

부하가 몰리거나 외부가 죽었을 때 무엇을 포기하고 무엇을 지킬지를 코드로 결정했고,
그 결정을 부하 테스트로 수치화했다. 아래는 각 결정의 문제(P) → 대안 분석(A) →
행동(구현) → 결과(R)다.

---

## 목표 구조: 4계층 방어

```
검색 요청
 → [1] Rate Limiter (IP별 Token Bucket) ──초과──▶ 429 (안전한 거부)
 → [2] Circuit Breaker (외부 AI 죽으면 빠른 실패) ──열림──▶ Fallback
 → [3] Bulkhead (API별 동시성 격리) ──포화──▶ 대기/거부
 → [4] Graceful Degradation (과부하 시 TTS→스트리밍 순 포기)
 → 정상 처리 (+ 답변 캐시로 반복 질문 즉시 응답)
```

앞단일수록 싸게 막는다. Rate Limiter는 요청을 받자마자 429로 끊어 외부 호출까지
가지 않게 하고, 뒤로 갈수록 실제 자원을 쓴다.

---

## [1] Rate Limiter — 한 사용자의 폭주가 전체를 무너뜨리지 않게

문제
한 사용자(혹은 버그난 클라이언트)가 초당 수십 건을 쏟으면, 그 요청들이 외부 AI의
요청 제한을 다 먹어치워 다른 정상 사용자까지 429를 맞는다. 한 명의 실수가 전체
장애로 번진다. 이걸 가장 앞단에서 막아야 한다.

대안 분석

| 방식 | 특징 | 판단 |
|---|---|---|
| Fixed Window | 1분에 N개. 구현 쉬움 | 창 경계에서 2배 몰림(59초 N개 + 61초 N개) |
| Sliding Window | 경계 문제 해결 | 요청 시각을 다 기록해 메모리/계산 비쌈 |
| Leaky Bucket | 일정 속도로만 흘림 | 정상적인 짧은 버스트도 못 봐줌(결제 API엔 적합) |
| Token Bucket | 버스트 허용 + 평균 제한 | 채용 |

검색은 "평소엔 뜸하다가 가끔 몰아치는" 트래픽이라, 버킷에 토큰이 차 있으면 순간
버스트(capacity까지)를 허용하고 지속 요청은 refill 속도로 제한하는 Token Bucket이
가장 맞았다.

구현과 근거
직접 구현했다([server/src/resilience/rateLimiter.ts](../server/src/resilience/rateLimiter.ts)).
타이머로 토큰을 채우지 않고, 요청이 올 때 "마지막 채운 시각~지금" 사이 흐른 시간만큼
계산해서 채운다(지연 계산). 타이머를 IP마다 돌리는 낭비를 없앤다. 키는
X-Forwarded-For(프록시 뒤 실제 IP) 우선. 검색뿐 아니라 음성(/api/voice)도 같은
버킷을 쓴다 — 음성을 빼면 반복 호출만으로 ElevenLabs 월 무료 한도를 고갈시킬 수 있다.

알려진 한계: X-Forwarded-For는 클라이언트가 직접 조작할 수 있는 헤더라, 프록시를
거치지 않고 서버를 바로 때리면 가짜 IP로 rate limit을 우회할 수 있다(부하 테스트가
가상 사용자를 만드는 방법이 정확히 이것이다). 실무에선 Express의 `trust proxy`로
신뢰할 프록시 홉 수를 지정하고 `req.ip`를 쓰는 게 정석이다. 단일 데모 서버라
지금은 단순한 쪽을 택했다.

결과 (실측)
capacity 5, refill 2/s에서 한 IP로 12연발 → 처음 7건 통과(버스트 + 그사이 회복),
이후 429. 같은 순간 다른 IP는 전부 통과. 사용자별 격리가 동작한다.
유닛 테스트 4개로 버스트 소진, 시간 회복, capacity 상한, key 독립을 고정했다.

대안·확장
직접 구현 대신 `rate-limiter-flexible`(메모리/Redis/Postgres 백엔드 교체 가능)를
쓰는 게 실무에선 더 흔하다. 대규모라면 앱 코드가 아니라 nginx `limit_req`나
Kong/Envoy 같은 API Gateway에서 앱 진입 전에 막는다. 여기서 직접 짠 건 Token Bucket
원리를 이해하고 있음을 코드로 보이기 위해서다.

## [2] Circuit Breaker — 죽은 곳을 계속 두드리지 않게

문제
외부 AI가 죽어서 매 호출이 타임아웃까지 매달리면, 사용자는 5초씩 기다렸다 에러를
받고 서버 자원(연결/메모리)도 헛되이 묶인다. 대형 장애 대부분이 "죽은 의존성을
계속 호출하다 연쇄로 무너진" 케이스다.

대안 분석

| 방식 | 특징 | 판단 |
|---|---|---|
| 재시도만 | 일시 오류엔 좋지만 | 진짜 죽었을 때 재시도가 오히려 부하를 키움 |
| opossum | Node 표준 CB 라이브러리 | 검증됨. CB만 담당 |
| cockatiel | 최신. CB+retry+timeout+bulkhead 통합 | 지금 내가 4겹으로 짠 걸 하나로 대체 가능 |
| Resilience4j | Java/Spring 표준 | 스택이 다름 |
| Hystrix | Netflix 원조 | 유지보수 종료(deprecated). 새 프로젝트 비추천 |
| Istio/Envoy outlier detection | 서비스 메시 레벨 | 앱 코드 없이 인프라가 처리 |

구현과 근거
직접 구현했다([circuitBreaker.ts](../server/src/resilience/circuitBreaker.ts)).
closed→open→half-open 3상태로, 연속 실패가 임계치(기본 5)를 넘으면 회로를 열어
즉시 실패시키고, resetMs(기본 10초) 뒤 시험 호출(half-open) 한 번으로 회복을
확인한다. 임계치 5는 "일시적 깜빡임은 재시도가 흡수하고, 그걸 넘는 연속 실패만
회로를 여는" 선으로 잡았다. 자체 구현은 상태 전이를 유닛 테스트로 증명하기 위함이다.

결과 (실측, 실패율 50% 장애 상황)

| | 서킷 ON | 서킷 OFF |
|---|---|---|
| 벽시계 | 8.9초 | 16.5초 |
| p50 지연 | 649ms | 3924ms |
| 빠른 실패(circuit_open) | 97건 | 0건 |

죽은 API를 97번 빠르게 차단해 벽시계를 절반, p50을 6배 줄였다. 성공률 자체는 서킷
ON이 낮은데(30% vs 46%), 이건 트레이드오프다 — 서킷은 "지금 죽었으니 빨리 실패하고
나중에 회복하자"를 택한다. 사용자가 8초 매달린 뒤 실패하는 것보다 0.6초에 실패를
알고 재시도하는 게 낫다는 판단이다.

최신 기술 메모
opossum이 표준이지만 cockatiel이 더 최신이고, circuit breaker + retry + timeout +
bulkhead를 한 라이브러리에서 정책으로 조합한다(.NET Polly의 Node 판). 프로덕션이라면
자체 구현 4겹을 cockatiel 하나로 바꾸는 게 유지보수에 낫다.

## [3] Bulkhead — 한 API가 자원을 다 먹어도 다른 기능은 살게

문제
배의 방수격벽처럼, 한 외부 API가 느려져 요청이 쌓여도 다른 기능까지 같이 죽으면
안 된다. Gemini가 막혔다고 음성(ElevenLabs)이나 검색(Exa)까지 멈추면 안 된다.

대안 분석
Semaphore(운영체제 개념)를 애플리케이션 레벨로 가져왔다. 외부 의존성마다 별도
세마포어를 둬서 동시 실행 수를 격리했다([guards.ts](../server/src/guards.ts)) — gemini,
exa, elevenlabs가 각자의 슬롯을 가지므로 하나가 포화돼도 다른 건 영향받지 않는다.
이게 곧 Bulkhead 패턴이다.

- 고정 상한(예: 8) 대신 Netflix concurrency-limits의 적응형(관찰된 지연으로 상한을
  실시간 조절, TCP 혼잡제어와 유사한 AIMD)이 최신 방식이다. "몇이 딱 맞는지" 미리
  정할 필요가 없다는 게 장점이지만, 지금 스코프엔 고정 상한이 이해하기 쉽고 충분하다.
- 직접 구현 대신 `p-limit`/`p-queue`로도 동시성 제한이 가능하다.
- DB가 있었다면 read/write 커넥션 풀 분리, 나아가 PgBouncer 같은 외부 풀러로
  커넥션을 앱 밖에서 통제한다. 이 프로젝트는 DB가 없어 해당 없음.

결과
동시 요청이 몰려도 실제 외부 호출은 세마포어 상한까지만 나가, 외부 API 요청 제한을
넘지 않는다. 대시보드에서 gemini.inUse(실행 중)와 queued(대기)로 실시간 확인된다.

## [4] Graceful Degradation — 다 살리기보다 뭘 먼저 포기할지

문제
과부하가 정말 심하면 "다 살리기"는 불가능하다. 진짜 결정은 우선순위, 즉 무엇을
먼저 포기하고 무엇을 절대 사수할지다.

행동
voicesearch의 우선순위를 이렇게 정하고 4단계로 구현했다([runtimeConfig.ts](../server/src/runtimeConfig.ts)):

| 레벨 | 포기하는 것 | 지키는 것 |
|---|---|---|
| none | (없음) | 전부 |
| no-tts | 음성 합성(가장 무겁고 덜 핵심) | 검색 + 스트리밍 |
| cache-only | 새 외부 호출 | 캐시된 답변 |
| reject | 새 검색 자체 | 서버/외부 자원 |

음성 합성이 가장 먼저 포기 대상인 이유: 외부 호출 + 오디오 전송으로 가장 무겁고,
실패해도 프론트가 브라우저 내장 음성으로 폴백해 경험이 완전히 끊기지 않는다.

결과
대시보드에서 레벨을 reject로 주입하면 새 검색은 즉시 거부되고 음성은 503으로
폴백을 유도한다. 지금은 수동(대시보드/주입)이지만, 세마포어 큐 길이나 서킷 상태를
보고 자동으로 레벨을 올리는 것으로 확장할 수 있다.

면접 질문 대비: "과부하 시 뭘 먼저 껐나요?" → "음성 합성입니다. 가장 무겁고, 꺼도
브라우저 음성으로 대체돼 핵심(검색 답변)은 지켜지니까요."

## 그 외: 캐시 · 재시도 · 타임아웃

답변 캐시 (LRU + TTL, [cache.ts](../server/src/resilience/cache.ts))
같은 질문이 다시 오면 LLM 호출(5~7초 + 비용)을 통째로 건너뛴다. 실측:

| | 캐시 ON | 캐시 OFF |
|---|---|---|
| p50 지연 | 1ms | 3905ms |
| 처리율 | 32.4 req/s | 12.1 req/s |

반복 질문이 섞인 부하에서 p50이 3905ms→1ms, 처리율 2.7배가 됐다. Map의 삽입 순서
성질로 LRU를, 저장 시각으로 TTL을 구현했다. 대안은 `lru-cache`(더 정교), 서버가
여러 대가 되면 Redis(문서 [8장 확장] 참고). 지금은 단일 인스턴스라 인메모리로 충분.

재시도 (지수 백오프)
429/5xx 같은 일시 오류만 0.5s→1s→2s로 재시도한다. 401(키 오류) 같은 건 재시도해도
소용없어 바로 던진다. 단, 스트림을 여는 것까지만 재시도한다 — 토큰이 이미 흐르기
시작하면 재시도가 화면에 답을 중복으로 붙이기 때문이다.

타임아웃
모든 외부 호출에 상한을 건다. 응답 없이 매달리는 요청이 자원을 붙잡고 쌓이는 걸
막는다. 이 넷(서킷/재시도/세마포어/타임아웃)을 한 겹으로 씌운 게
[guard.ts](../server/src/resilience/guard.ts)다.

## 부하 테스트 방법론

핵심 결정: 실제 Gemini에는 부하를 줄 수 없다(요청 제한 + 비용, 그리고 무의미). 그래서
외부 LLM을 "느리고 가끔 실패하는" mock으로 격리했다([mockLlm.ts](../server/src/mockLlm.ts)).
그러면 남는 변수는 내 서버 계층뿐이라, 회복탄력성만 순수하게 측정된다. 실패율/지연은
런타임에 조절해 평온/장애/과부하 시나리오를 재현한다.

측정 도구
- 자체 스크립트([loadtest/run.mts](../loadtest/run.mts)): SSE를 done까지 읽어 캐시
  히트/폴백 같은 시나리오 지표와 클라 측 p50/p95/p99를 집계. SSE 스트리밍은 표준
  도구가 "완료 시간"을 재기 어려워 직접 만들었다.
- k6([loadtest/k6-throughput.js](../loadtest/k6-throughput.js),
  [k6-ratelimit.js](../loadtest/k6-ratelimit.js)): 표준 도구로 단계적 부하 증가와
  임계(threshold) 자동 판정, 429 차단율 측정.
- 서버 자체 메트릭(/api/metrics): 서킷 상태, 세마포어 점유, 캐시 적중률을 서버가
  스스로 집계해 클라 측정과 교차 검증.

## 관측성 — 방어가 언제 발동했는지 보여야 결정할 수 있다

방어 로직은 "언제 발동했는지" 볼 수 있어야 실제 장애에서 몇 초 안에 원인을 짚고
결정을 내릴 수 있다.

- 구조화 로깅(pino): 로그를 JSON 한 줄로 남겨 나중에 기계로 집계 가능하게 했다.
- 인메모리 메트릭([metrics.ts](../server/src/metrics.ts)): 지연 백분위(p50/p95/p99),
  결과별 카운트, 캐시 적중률. 평균이 아니라 백분위를 보는 이유는, 평균이 느린 5%를
  가려버려 사용자 체감(SLO)은 p95에서 갈리기 때문이다.
- 실시간 대시보드([web/src/Dashboard.tsx](../web/src/Dashboard.tsx)): 메트릭을 1초마다
  폴링해 그래프로 그리고, 장애/부하를 주입하는 버튼을 둔다. "외부 AI 죽이기"를 누르면
  서킷이 open(빨강)으로 바뀌고 요청 그래프가 튀는 걸 실시간으로 관찰할 수 있다.

메트릭이 인메모리라 서버가 죽으면 사라진다. 프로덕션이라면 Prometheus로 내보내고
Grafana로 대시보드를 그리는 게 표준이다(지금 대시보드가 그 축소판).

## 서버 자체의 생존 — 외부 의존성 밖의 장애

위까지는 외부 AI가 흔들릴 때의 방어였다. 하지만 실제 서비스에선 서버 프로세스
자체와 배포 과정에서도 장애가 난다. 이 변수들도 처리했다.

| 변수 | 처리 |
|---|---|
| 클라이언트 연결 끊김(탭 닫기 등) | res 'close' 감지 → 스트림 소비 중단, 죽은 소켓에 쓰지 않음, 잘린 부분 답변은 캐시하지 않음 |
| 프로세스 크래시 | uncaughtException/unhandledRejection을 로그로 남김(최후 안전망) |
| 배포 재시작(SIGTERM) | Graceful shutdown: 새 연결은 차단하고 진행 중 요청은 마무리, 10초 안에 안 끝나면 강제 종료 |
| 헬스체크 | /api/health로 로드밸런서/배포 플랫폼이 인스턴스 생사를 확인 |
| 큰 페이로드 | 본문 16kb 제한(검색 질문은 200자라 충분) |
| CORS | 프로덕션은 FRONTEND_URL만 허용, 로컬은 개방 |
| 장애 주입 엔드포인트 노출 | 대시보드용 /api/admin/config, /api/metrics/reset은 ADMIN_TOKEN 헤더 검사. 토큰 없이 프로덕션이면 차단(CORS는 브라우저만 막을 뿐 curl은 못 막으므로 별도 인증이 필요) |

연결 끊김을 처리하는 이유가 특히 중요하다. 사용자가 검색 도중 탭을 닫으면, 그걸
모르는 서버는 계속 외부 AI를 호출하고 이미 죽은 소켓에 쓰려다 에러를 낸다. 부하가
몰릴 때 이런 좀비 작업이 쌓이면 자원이 낭비된다. res의 close 이벤트로 이걸 감지해
생성 소비를 멈춘다.

한계: 타임아웃이 reject해도 이미 시작된 외부 호출 자체는 취소되지 않는다(SDK에
AbortController 미적용). 타임아웃 후에도 그 호출이 자원을 잠깐 더 쓴다. 다음 과제다.

## 사람이 몰리면 감당되나 — 정직한 답

한 대(단일 인스턴스)로는 몰려도 죽지 않는다. Rate Limiter가 429로 안전하게 거부하고,
세마포어가 외부 호출을 상한까지만 내보내고, 캐시가 반복을 흡수한다. "터지는" 게
아니라 "초과분을 정중히 거부"한다.

단, 처리량 자체는 외부 LLM 속도(5~7초)에 묶여 낮다. 많이 몰리면 상당수가 429를
받는다. 안전하지만 서비스는 사실상 거부 상태가 된다.

진짜 대규모는 여러 대로 늘려야 하는데, 여기 함정이 있다. Rate Limiter·캐시·메트릭이
전부 인메모리라, 인스턴스를 늘리면 상태를 공유하지 못한다. 사용자가 3대에 분산되면
rate limit이 실질 3배로 느슨해지고, 캐시 히트율이 떨어지고, 메트릭이 파편화된다.
그래서 수평 확장을 하려면 이 상태들을 Redis로 빼야 한다(rate limit 카운터,
공유 캐시, 메트릭 집계). 이게 다음 단계다.

## 이 아키텍처에 일부러 두지 않은 것 (정직한 스코프)

채팅 시스템의 견고함 논의에서 자주 나오는 결정 포인트 중, 이 프로젝트에 해당하지
않는 것들을 억지로 넣지 않았다. voicesearch는 메시지를 저장/전달하는 채팅이 아니라,
상태 없는(stateless) 요청-응답 검색이기 때문이다.

- 메시지 유실 방지(DB 먼저 쓰고 알림): 저장할 메시지가 없다. DB 자체가 없다.
- 재시도 안전성(Idempotency): 채팅의 "중복 저장 방지"는 해당 없음. 다만 "같은 요청
  중복 처리 방지"는 답변 캐시가 부분적으로 수행한다(같은 질문은 외부 호출 없이 캐시).
- Pub/Sub 실시간 전달: 실시간 브로드캐스트가 없는 단발 검색이라 불필요.
- 오토스케일링: 인프라 레벨 결정으로 앱 코드 밖. 급증이 예측되면 미리 스케일업.

이걸 "몰라서 뺀 것"과 구분하려고 여기 적었다. 채팅이었다면 각각 DB 우선 쓰기,
메시지 고유 ID 중복 제거, 메시지 큐(BullMQ 등)로 구현했을 것이다.

## 메타 포인트: 앱 코드 vs 인프라

위 대안들을 보면 축이 하나 반복된다 — "애플리케이션 코드로 직접 짤 것이냐, 인프라(API
Gateway / Service Mesh)에 맡길 것이냐". 이 프로젝트는 전부 앱 코드 레벨을 택했는데,
목적이 "이해하고 있음을 코드로 증명"하는 포트폴리오이기 때문이다. 실무 대규모
서비스라면 rate limit, circuit breaker 상당수가 Envoy/API Gateway 같은 인프라 레벨로
넘어간다.

면접에서 "왜 인프라 대신 코드로 짰나요?"가 나오면: "지금 스코프에선 이해도 증명이
목적이었고, 프로덕션 확장 시엔 인프라 레벨로 옮기는 게 맞다고 판단했습니다."

| 레이어 | 이 프로젝트 | 라이브러리 | 인프라 레벨 |

| 관측 | 인메모리+대시보드 | — | Prometheus + Grafana |

## 한계와 다음

- 타임아웃은 스트림을 여는 것까지만 건다. 스트림 소비 중 토큰이 느리게 오는 경우의
  idle timeout은 다음 과제다.
- Graceful Degradation이 수동(주입)이다. 세마포어 큐/서킷 상태로 자동 발동하게
  확장할 수 있다.
- 메트릭이 인메모리라 단일 인스턴스 전제다. 여러 대가 되면 Prometheus로 옮긴다.
- 동시성 상한이 고정값이다. Netflix 적응형(AIMD)으로 바꾸면 상한을 미리 정할 필요가
  없다.
