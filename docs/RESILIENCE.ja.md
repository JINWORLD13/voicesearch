# レジリエンス設計 (Resilience)

このプロジェクトのサーバーは、遅く(応答5〜7秒)、断続的に失敗し(429/503)、
リクエスト制限のある外部AI APIをラップするゲートウェイ。したがって
「どれだけ多く処理するか」ではなく「外部が揺れても自分のサーバーがどう耐えるか」が
核心の課題になる。

負荷が集中したとき、あるいは外部が死んだときに、何を捨てて何を守るのかをコードで
決め、その判断を負荷テストで数値化した。以下は各決定の問題(P) → 代替案分析(A) →
行動(実装) → 結果(R)。

---

## 目標構造: 4層防御

```
検索リクエスト
 → [1] Rate Limiter (IPごとのToken Bucket) ──超過──▶ 429 (安全な拒否)
 → [2] Circuit Breaker (外部AIが死んだら即時失敗) ──開放──▶ Fallback
 → [3] Bulkhead (APIごとの並行性隔離) ──飽和──▶ 待機/拒否
 → [4] Graceful Degradation (過負荷時はTTS→ストリーミングの順に断念)
 → 正常処理 (+ 回答キャッシュで同じ質問に即応答)
```

前段ほど安く止める。Rate Limiterはリクエストを受けた瞬間に429で切り、外部呼び出しまで
到達させない。後段に行くほど実際のリソースを使う。

---

## [1] Rate Limiter — 一人の暴走が全体を倒さないように

問題
一人のユーザー(あるいはバグったクライアント)が毎秒数十件を投げると、そのリクエストが
外部AIのリクエスト制限を食い尽くし、他の正常なユーザーまで429を食らう。一人のミスが
全体障害に波及する。これを最前段で止めなければならない。

代替案分析

| 方式 | 特徴 | 判断 |
|---|---|---|
| Fixed Window | 1分にN個。実装が容易 | ウィンドウ境界で2倍集中(59秒にN個 + 61秒にN個) |
| Sliding Window | 境界問題を解決 | リクエスト時刻を全部記録するのでメモリ/計算が高価 |
| Leaky Bucket | 一定速度でのみ流す | 正常な短いバーストも許容できない(決済APIには適する) |
| Token Bucket | バースト許容 + 平均制限 | 採用 |

検索は「普段は疎で、たまに集中する」トラフィックなので、バケットにトークンが
溜まっていれば瞬間的なバースト(capacityまで)を許し、持続的なリクエストはrefill速度で
制限するToken Bucketが最も合っていた。

実装と根拠
自作した([server/src/resilience/rateLimiter.ts](../server/src/resilience/rateLimiter.ts))。
タイマーでトークンを補充するのではなく、リクエストが来たときに「最後に補充した時刻〜今」の
経過時間ぶんだけ計算して補充する(遅延計算)。IPごとにタイマーを回す無駄をなくす。キーは
X-Forwarded-For(プロキシ背後の実IP)を優先。検索だけでなく音声(/api/voice)も同じ
バケットを使う — 音声を外すと、繰り返し呼び出すだけでElevenLabsの月間無料枠を
使い果たせてしまう。

既知の限界: X-Forwarded-Forはクライアントが自分で書き換えられるヘッダーなので、
プロキシを経由せずサーバーを直接叩けば偽のIPでrate limitを回避できる(負荷テストが
仮想ユーザーを作る方法がまさにこれだ)。実務ではExpressの `trust proxy` で信頼する
プロキシのホップ数を指定し、`req.ip` を使うのが定石。単一のデモサーバーなので、
今は単純な方を選んだ。

結果 (実測)
capacity 5、refill 2/s で1つのIPから12連発 → 最初の7件が通過(バースト + その間の回復)、
以降は429。同じ瞬間に別のIPは全件通過。ユーザーごとの隔離が機能している。
ユニットテスト4つで、バースト消費・時間回復・capacity上限・キー独立を固定した。

代替案・拡張
自作の代わりに `rate-limiter-flexible`(メモリ/Redis/Postgresのバックエンドを差し替え可能)を
使うのが実務ではより一般的。大規模ならアプリコードではなくnginxの `limit_req` や
Kong/Envoyのようなアプリ手前のAPI Gatewayで止める。ここで自作したのは、Token Bucketの
原理を理解していることをコードで示すため。

## [2] Circuit Breaker — 死んだ相手を叩き続けないように

問題
外部AIが死んで毎回の呼び出しがタイムアウトまでぶら下がると、ユーザーは5秒ずつ待たされて
エラーを受け取り、サーバーのリソース(コネクション/メモリ)も無駄に拘束される。大規模障害の
多くが「死んだ依存を呼び続けて連鎖的に崩れた」ケース。

代替案分析

| 方式 | 特徴 | 判断 |
|---|---|---|
| 再試行のみ | 一時的エラーには良いが | 本当に死んだときは再試行がむしろ負荷を増やす |
| opossum | Node標準のCBライブラリ | 実績あり。CBのみ担当 |
| cockatiel | 最新。CB+retry+timeout+bulkheadを統合 | 今4重で書いたものを1つで代替可能 |
| Resilience4j | Java/Springの標準 | スタックが違う |
| Hystrix | Netflixの元祖 | メンテ終了(deprecated)。新規プロジェクトには非推奨 |
| Istio/Envoy outlier detection | サービスメッシュレベル | アプリコードなしでインフラが処理 |

実装と根拠
自作した([circuitBreaker.ts](../server/src/resilience/circuitBreaker.ts))。
closed→open→half-openの3状態で、連続失敗がしきい値(デフォルト5)を超えたら回路を開いて
即座に失敗させ、resetMs(デフォルト10秒)後の試験呼び出し(half-open)1回で回復を確認する。
しきい値5は「一時的な瞬断は再試行が吸収し、それを超える連続失敗だけ回路を開く」線として
設定した。自作したのは状態遷移をユニットテストで証明するため。

結果 (実測、失敗率50%の障害状況)

| | サーキットON | サーキットOFF |
|---|---|---|
| 壁時計時間 | 8.9秒 | 16.5秒 |
| p50レイテンシ | 649ms | 3924ms |
| 即時失敗(circuit_open) | 97件 | 0件 |

死んだAPIを97回すばやく遮断し、壁時計時間を半分、p50を6倍縮めた。成功率自体は
サーキットONの方が低いが(30% vs 46%)、これはトレードオフだ — サーキットは「今は
死んでいるので早く失敗し、後で回復しよう」を選ぶ。ユーザーが8秒ぶら下がった末に
失敗するより、0.6秒で失敗を知って再試行できる方が良いという判断。

最新技術メモ
opossumが標準だがcockatielの方が新しく、circuit breaker + retry + timeout + bulkheadを
1つのライブラリでポリシーとして組み合わせられる(.NET PollyのNode版)。プロダクションなら
自作の4重をcockatiel 1つに置き換える方が保守しやすい。

## [3] Bulkhead — 1つのAPIがリソースを食い尽くしても他の機能は生きるように

問題
船の防水隔壁のように、1つの外部APIが遅くなってリクエストが溜まっても、他の機能まで
一緒に死んではいけない。Geminiが詰まったからといって音声(ElevenLabs)や検索(Exa)まで
止まってはならない。

代替案分析
Semaphore(OSの概念)をアプリケーションレベルに持ち込んだ。外部依存ごとに別々の
セマフォを置いて同時実行数を隔離した([guards.ts](../server/src/guards.ts)) — gemini、
exa、elevenlabsがそれぞれのスロットを持つので、1つが飽和しても他は影響を受けない。
これがすなわちBulkheadパターン。

- 固定上限(例: 8)の代わりに、Netflixのconcurrency-limitsの適応型(観測したレイテンシで
  上限をリアルタイム調整、TCP輻輳制御に似たAIMD)が最新の方式。「いくつが適切か」を
  事前に決める必要がないのが利点だが、今のスコープでは固定上限の方が理解しやすく十分。
- 自作の代わりに `p-limit`/`p-queue` でも並行数制限は可能。
- DBがあればread/writeのコネクションプール分離、さらにPgBouncerのような外部プーラーで
  コネクションをアプリの外から制御する。このプロジェクトはDBがないので該当なし。

結果
同時リクエストが集中しても実際の外部呼び出しはセマフォ上限までしか出ないので、外部APIの
リクエスト制限を超えない。ダッシュボードで gemini.inUse(実行中)と queued(待機)として
リアルタイムに確認できる。

## [4] Graceful Degradation — 全部守るより、何を先に捨てるか

問題
過負荷が本当に厳しいとき「全部守る」は不可能。本当の決定は優先順位、つまり何を先に
捨てて何を絶対に死守するか。

行動
voicesearchの優先順位をこう定め、4段階で実装した([runtimeConfig.ts](../server/src/runtimeConfig.ts)):

| レベル | 捨てるもの | 守るもの |
|---|---|---|
| none | (なし) | 全部 |
| no-tts | 音声合成(最も重く、最も本質から遠い) | 検索 + ストリーミング |
| cache-only | 新規の外部呼び出し | キャッシュ済みの回答 |
| reject | 新規検索そのもの | サーバー/外部リソース |

音声合成が最初に捨てられる理由: 外部呼び出し + オーディオ転送で最も重く、失敗しても
フロントがブラウザ内蔵音声にフォールバックするため体験が完全には途切れない。

結果
ダッシュボードでレベルをrejectに注入すると新規検索は即座に拒否され、音声は503で
フォールバックを促す。今は手動(ダッシュボード/注入)だが、セマフォのキュー長や
サーキットの状態を見て自動でレベルを上げるように拡張できる。

面接想定: 「過負荷時に何を最初に切りましたか?」→「音声合成です。最も重く、切っても
ブラウザ音声で代替されるので、核心(検索の回答)は守られるからです。」

## その他: キャッシュ・再試行・タイムアウト

回答キャッシュ (LRU + TTL, [cache.ts](../server/src/resilience/cache.ts))
同じ質問が再び来たらLLM呼び出し(5〜7秒 + コスト)をまるごとスキップする。実測:

| | キャッシュON | キャッシュOFF |
|---|---|---|
| p50レイテンシ | 1ms | 3905ms |
| スループット | 32.4 req/s | 12.1 req/s |

繰り返しの質問が混ざる負荷で p50が3905ms→1ms、スループット2.7倍になった。Mapの挿入順序の
性質でLRUを、保存時刻でTTLを実装した。代替は `lru-cache`(より精緻)、サーバーが複数台に
なればRedis(下の水平スケールの項を参照)。今は単一インスタンスなのでインメモリで十分。

再試行 (指数バックオフ)
429/5xxのような一時的エラーだけを 0.5s→1s→2s で再試行する。401(キーエラー)のようなものは
再試行しても無駄なので即座に投げる。ただし、再試行するのはストリームを開くところまでだ —
トークンが流れ始めた後に再試行すると、画面に出た回答の上に重複して追記されてしまうから。

タイムアウト
すべての外部呼び出しに上限をかける。応答なくぶら下がるリクエストがリソースを掴んだまま
溜まるのを防ぐ。この4つ(サーキット/再試行/セマフォ/タイムアウト)を1枚に被せたのが
[guard.ts](../server/src/resilience/guard.ts)。

## 負荷テストの方法論

核心の判断: 実際のGeminiに負荷はかけられない(リクエスト制限 + コスト、そして無意味)。
そこで外部LLMを「遅くて時々失敗する」mockに隔離した([mockLlm.ts](../server/src/mockLlm.ts))。
そうすれば残る変数は自分のサーバー層だけになり、レジリエンスだけを純粋に測定できる。
失敗率/レイテンシはランタイムに調整して、平常/障害/過負荷のシナリオを再現する。

測定ツール
- 自作スクリプト([loadtest/run.mts](../loadtest/run.mts)): SSEをdoneまで読んで、キャッシュ
  ヒットやフォールバックといったシナリオ指標とクライアント側のp50/p95/p99を集計。SSE
  ストリーミングは標準ツールで「完了時間」を測りにくいので自作した。
- k6([loadtest/k6-throughput.js](../loadtest/k6-throughput.js),
  [k6-ratelimit.js](../loadtest/k6-ratelimit.js)): 標準ツールで段階的な負荷増加と
  しきい値(threshold)の自動判定、429の遮断率を測定。
- サーバー自身のメトリクス(/api/metrics): サーキット状態、セマフォ占有、キャッシュ
  ヒット率をサーバーが自ら集計し、クライアント側の測定とクロス検証。

## 可観測性 — 防御がいつ発動したか見えて初めて判断できる

防御ロジックは「いつ発動したか」が見えて初めて、実際の障害で数秒のうちに原因を特定して
判断を下せる。

- 構造化ロギング(pino): ログをJSON 1行で残し、後で機械的に集計できるようにした。
- インメモリメトリクス([metrics.ts](../server/src/metrics.ts)): レイテンシのパーセンタイル
  (p50/p95/p99)、結果別のカウント、キャッシュヒット率。平均ではなくパーセンタイルを見る
  理由は、平均が遅い5%を覆い隠してしまい、ユーザーの体感(SLO)はp95で決まるから。
- リアルタイムダッシュボード([web/src/Dashboard.tsx](../web/src/Dashboard.tsx)): メトリクスを
  1秒ごとにポーリングしてグラフに描き、障害/負荷を注入するボタンを置く。「外部AIを殺す」を
  押すとサーキットがopen(赤)に変わり、リクエストのグラフが跳ねるのをリアルタイムで観察できる。

メトリクスがインメモリなのでサーバーが死ぬと消える。プロダクションならPrometheusに
エクスポートしてGrafanaでダッシュボードを描くのが標準だ(今のダッシュボードはその縮小版)。

## サーバー自体の生存 — 外部依存の外側の障害

ここまでは外部AIが揺れたときの防御だった。しかし実サービスではサーバープロセス自体や
デプロイの過程でも障害が起きる。これらの変数も処理した。

| 変数 | 対処 |
|---|---|
| クライアントの切断(タブを閉じるなど) | res の 'close' を検知 → ストリーム消費を中断、死んだソケットに書き込まない、途中で切れた部分回答はキャッシュしない、成功ではなく中断(requests.aborted)として別途集計 |
| プロセスクラッシュ | uncaughtException/unhandledRejection をログに残す(最後の安全網) |
| デプロイ再起動(SIGTERM) | Graceful shutdown: 新規接続は遮断し、処理中のリクエストは完了させる。10秒で終わらなければ強制終了 |
| ヘルスチェック | /api/health でロードバランサー/デプロイ基盤がインスタンスの生死を確認 |
| 大きなペイロード | ボディ16kb制限(検索の質問は200文字なので十分) |
| CORS | プロダクションはFRONTEND_URLのみ許可、ローカルは開放 |
| 障害注入エンドポイントの露出 | ダッシュボード用の /api/admin/config、/api/metrics/reset はデフォルトで公開(訪問者が障害注入を体験できるのがデモの意図)。代わりに放置された操作は最終操作の10分後に自動で正常化され、ADMIN_TOKEN を設定すれば x-admin-token ヘッダー検査でロックできる(CORSはブラウザしか止められず、curlは止められないのでロックは認証でのみ可能) |

切断を処理する理由が特に重要。ユーザーが検索の途中でタブを閉じると、それを知らない
サーバーは外部AIを呼び続け、すでに死んだソケットに書き込もうとしてエラーを出す。負荷が
集中するときにこうしたゾンビ作業が溜まるとリソースの無駄になる。resのcloseイベントで
これを検知し、生成の消費を止める。

限界: タイムアウトがrejectしても、すでに始まった外部呼び出し自体はキャンセルされない
(SDKにAbortController未適用)。タイムアウト後もその呼び出しがしばらくリソースを使う。
次の課題。

## 人が集中したら耐えられるのか — 正直な答え

1台(単一インスタンス)でも、集中しても死にはしない。Rate Limiterが429で安全に拒否し、
セマフォが外部呼び出しを上限までしか出さず、キャッシュが繰り返しを吸収する。「破裂する」
のではなく「超過分を丁重に拒否する」。

ただしスループット自体は外部LLMの速度(5〜7秒)に縛られて低い。多く集中すれば相当数が429を
受け取る。安全ではあるが、サービスとしては事実上の拒否状態になる。

本当の大規模は複数台に増やす必要があるが、ここに落とし穴がある。Rate Limiter・キャッシュ・
メトリクスがすべてインメモリなので、インスタンスを増やすと状態を共有できない。ユーザーが
3台に分散するとrate limitが実質3倍に緩くなり、キャッシュヒット率が落ち、メトリクスが
断片化する。したがって水平スケールするにはこれらの状態をRedisに出す必要がある(rate limitの
カウンター、共有キャッシュ、メトリクス集計)。これが次のステップ。

## このアーキテクチャに意図的に入れなかったもの (正直なスコープ)

チャットシステムの堅牢性の議論でよく出る決定ポイントのうち、このプロジェクトに該当しない
ものを無理に入れなかった。voicesearchはメッセージを保存/配送するチャットではなく、
状態を持たない(stateless)リクエスト-レスポンス型の検索だから。

- メッセージ消失防止(DBに先に書いてから通知): 保存するメッセージがない。DB自体がない。
- 再試行の安全性(Idempotency): チャットの「重複保存の防止」は該当なし。ただし「同じ
  リクエストの重複処理の防止」は回答キャッシュが部分的に担う(同じ質問は外部呼び出しなしで
  キャッシュから)。
- Pub/Subのリアルタイム配信: リアルタイムのブロードキャストがない単発検索なので不要。
- オートスケーリング: インフラレベルの決定でアプリコードの外。急増が予測されるなら事前に
  スケールアップ。

これを「知らなくて外したもの」と区別するためにここに書いた。チャットだったら、それぞれ
DBへの先行書き込み、メッセージ固有IDでの重複排除、メッセージキュー(BullMQなど)で
実装しただろう。

---

## メタな論点: アプリコード vs インフラ

上の代替案を見ると、軸が1つ繰り返し現れる —「アプリケーションコードで自作するのか、
インフラ(API Gateway / Service Mesh)に任せるのか」。このプロジェクトはすべてアプリコード
レベルを選んだが、目的が「理解していることをコードで証明する」ポートフォリオだから。
実務の大規模サービスなら、rate limitやcircuit breakerの相当部分はEnvoy/API Gatewayのような
インフラレベルに移る。

面接で「なぜインフラではなくコードで書いたのか」と聞かれたら:「今のスコープでは理解度の
証明が目的で、プロダクションへ拡張する際はインフラレベルに移すのが正しいと判断しました。」

| Rate Limit | Token Bucket自作 | rate-limiter-flexible | nginx limit_req, Kong/Envoy |
| 並行性 | Semaphore自作 | p-limit, Netflix concurrency-limits | — |
| Circuit Breaker | 自作の3状態 | opossum, cockatiel(最新) | Istio/Envoy outlier detection |
| Bulkhead | APIごとのセマフォ | cockatiel | サービス分割 |
| キャッシュ | LRU+TTL自作 | lru-cache | Redis |
| 可観測性 | インメモリ+ダッシュボード | — | Prometheus + Grafana |

## 限界と次

- タイムアウトはストリームを開くところまでしかかけていない。ストリーム消費中に
  トークンが遅れて届く場合のidle timeoutは次の課題。
- Graceful Degradationが手動(注入)。セマフォのキュー/サーキットの状態で自動発動する
  よう拡張できる。
- メトリクスがインメモリなので単一インスタンス前提。複数台になればPrometheusへ移す。
- 並行数の上限が固定値。Netflixの適応型(AIMD)に替えれば上限を事前に決める必要がなくなる。
